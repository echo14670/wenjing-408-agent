# 项目接口说明

根据 stage2《架构图、数据字典、API契约规范》和《接口联调与开发交接》整理。线上字段定义以 [Apifox](https://hr124ptabw.apifox.cn/) 为准。

## 接口概览

| 接口 | 方法 | 请求格式 | 用途 |
| --- | --- | --- | --- |
| `/api/search` | POST | JSON | 检索题库，区分原题、相似题和未命中 |
| `/api/chat` | POST | JSON | 围绕当前题目直接解析或引导答疑 |
| `/api/upload` | POST | multipart/form-data | 解析 PDF、图片等文件，返回提取文本和失败信息 |

## 1. 查题：POST /api/search

### 请求

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `raw_input` | string | 用户输入的题干，或经用户确认的图片识别文本 |
| `input_type` | string | `text`：文字输入；`image`：来自图片识别。图片文件通过上传接口处理，不在此字段中传文件 |

```json
{
  "raw_input": "某 Cache 有 1024 行，采用四路组相联，组号占几位？",
  "input_type": "text"
}
```

### 响应

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `match_type` | string | `original`、`similar` 或 `miss` |
| `question_data` | object / null | 原题命中时的题目对象；相似或未命中时为 null |
| `similar_questions` | array | 相似题候选；原题命中或未命中时为空数组 |

原题命中示例（题目对象仅展示 stage2 原示例中的字段，内容为演示数据）：

```json
{
  "match_type": "original",
  "question_data": {
    "question_id": "Q001",
    "subject": "计算机组成原理",
    "stem": "某 Cache 有 1024 行，采用四路组相联，组号占几位？",
    "answer": "8位",
    "review_state": "verified"
  },
  "similar_questions": []
}
```

`question_id` 是题目 ID，`subject` 是学科，`stem` 是题干，`answer` 是答案，`review_state` 是核验状态。stage2 数据模型还列有 `solution`（解析）和 `source_ref`（来源）；完整响应字段及必填项按 Apifox 定义，不把这个简化示例当作完整字段清单。

未命中示例：

```json
{
  "match_type": "miss",
  "question_data": null,
  "similar_questions": []
}
```

相似题返回 `match_type="similar"`、`question_data=null` 和候选列表。相似候选仅供参考，不能把它的答案当作用户原题的核验答案；候选对象的具体字段以 Apifox 为准。

## 2. 答疑：POST /api/chat

### 请求

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `session_messages` | array | 对话消息，每条包含 `role`（user/assistant）和 `content`（文本）；携带完整原题和最近三轮对话 |
| `question_id` | string / null | 已确认原题的 ID；围绕用户自己的未收录题目答疑时为 null，不传相似候选的 ID |
| `user_answer` | string | 用户作答或思路；没有时传空字符串 |
| `mode` | string | `direct`：直接解析；`guided`：引导解题 |
| `context_chunks` | string[] | 前端从个人资料中切出的文本；没有时传空数组 |

```json
{
  "session_messages": [
    {"role": "user", "content": "某 Cache 有 1024 行，采用四路组相联，组号占几位？"},
    {"role": "user", "content": "四路是不是就说明组号占2位？"}
  ],
  "question_id": null,
  "user_answer": "我认为四路表示四组",
  "mode": "guided",
  "context_chunks": []
}
```

先放原题，再放最近的对话，避免后端只收到“为什么这样算”等缺少上下文的问题。相似与未命中时仍可询问用户自己的题目，不能把相似候选替换成当前题目。

### 响应

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `reply` | string | 模型讲解或引导提示 |
| `tool_result` | string | 工具计算结果；无结果或本轮不展示时为空字符串 |
| `citations` | string[] | 有依据的来源说明；没有可核验来源时为空数组 |

```json
{
  "reply": "四路表示每组有四行，不是总共只有四组。先用总行数除以每组行数，算算共有多少组？",
  "tool_result": "",
  "citations": []
}
```

`guided` 初始只给提示，不提前展示最终答案、完整解析或泄露答案的工具结果；用户主动查看答案后再展示完整解答。题库核验解析与模型讲解分开展示，发生冲突时不能覆盖原解析。没有来源依据时，不编造教材页码或真题年份。

## 3. 上传解析：POST /api/upload

### 请求

使用 `multipart/form-data`，字段名为 `file`，值为上传的文件。浏览器使用 FormData 时，由浏览器生成包含 boundary 的 Content-Type。

```javascript
const form = new FormData()
form.append('file', selectedFile)
const response = await fetch('/api/upload', {
  method: 'POST',
  body: form
})
```

### 响应

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `task_id` | string | 此次解析任务的标识 |
| `extracted_text` | string | 提取出的文本 |
| `failure_details` | array | 解析失败信息；无失败时为 `[]`。stage2 原接口示例未明确数组元素结构，按 Apifox 定义处理 |

```json
{
  "task_id": "task_12345",
  "extracted_text": "提取出来的文本内容……",
  "failure_details": []
}
```

题图识别后，由用户确认或修正题干，再调用 `/api/search`。个人资料解析后，前端预览、修正、去重，经用户确认才保存到本地资料库；答疑时切片填入 `context_chunks`。个人资料不写入后端资料数据库。

## 调用关系

- 文字搜题：输入题干 → `/api/search` → 展示检索结果 → `/api/chat` 答疑。
- 图片搜题：`/api/upload` → 确认识别文本 → `/api/search` → `/api/chat`。
- 个人资料：`/api/upload` → 预览确认 → 本地保存与切片 → 随 `/api/chat` 发送。

网络或解析失败不等于题库未命中，不能当作 `match_type="miss"` 处理。stage2 未完整定义各接口的错误响应、文件大小限制及所有必填项，这些以 Apifox 为准；本文不额外新增字段或错误码。

## 部署自检：GET /api/health

无需请求体。用于确认后端可响应、题库和检索索引已加载，建议保留。它不检查模型调用或 OCR 服务是否可用。

| 响应字段 | 说明 |
| --- | --- |
| status | 正常响应为 `ok` |
| questions | 已加载题目总数 |
| by_subject | 按学科统计的题目数量 |
| by_review_state | 按核验状态统计的题目数量 |
| skipped | 加载时跳过的记录数 |
| tokenizer | 当前分词器：jieba 或 fallback-bigram |
| indexed | 已建立检索索引的题目数 |

此接口已在 PR #3 实现，作为部署辅助接口单独登记，不改变三个学习接口的请求与响应。
